# ClipPro Product Direction

> 상태: Draft
> 문서 성격: Product canonical
> 최종 수정: 2026-07-18
> 관련 구현: 단계별 에픽으로 별도 정의

## 1. 문서 목적

이 문서는 ClipPro가 어떤 문제를 해결하는 제품인지, 어떤 원칙을 유지해야 하는지, 어떤 방식으로 수익화하고 확장할지를 정리한 제품 수준의 기준 문서다.

구체적인 구현 방법은 아키텍처 문서와 에픽에서 다룬다. 구현 과정에서 이 문서와 충돌하는 판단이 필요하다면, 구현 편의를 이유로 제품 원칙을 암묵적으로 변경하지 않고 제품 문서의 변경 여부를 먼저 검토한다.

## 2. 제품 정의

### 확정

ClipPro는 사진과 영상 등 개인 미디어를 중심으로 사용자가 자신의 데이터를 직접 정리하고 탐색하는 **로컬 우선 개인 데이터 관리 라이브러리**다.

ClipPro의 핵심 가치는 파일을 새로운 서비스 안으로 가져가 소유하는 데 있지 않다. 사용자가 이미 보유한 파일을 기반으로 태그, 클립, 인물, 컬렉션 및 검색 관계를 구성하고, 이를 빠르고 일관된 방식으로 탐색할 수 있게 하는 데 있다.

제품의 기본 문장은 다음과 같다.

> 내 데이터는 내 저장소에 있으며, ClipPro는 그 데이터를 더 잘 이해하고 관리할 수 있게 한다.

### 방향

ClipPro는 장기적으로 다양한 데이터 소스와 선택적 클라우드 서비스를 지원할 수 있다. 그러나 로컬 라이브러리는 항상 독립적으로 사용할 수 있어야 하며, 클라우드 사용 여부가 핵심 데이터 접근권을 결정해서는 안 된다.

## 3. 목표 사용자

### 현재 목표

- 많은 사진과 영상을 장기간 보유하고 있는 개인 사용자
- 운영체제 폴더 구조만으로는 원하는 분류와 탐색이 어려운 사용자
- 태그, 인물, 클립 및 컬렉션을 조합해 자신만의 기준으로 미디어를 관리하려는 사용자
- 외장 드라이브나 여러 로컬 저장소에 분산된 미디어를 하나의 라이브러리 관점에서 보고 싶은 사용자
- 클라우드 업로드 없이 개인 데이터를 관리하고 싶은 사용자

### 미래 확장 가능 사용자

- NAS나 네트워크 드라이브를 사용하는 고급 개인 사용자
- 여러 장치에서 동일한 개인 라이브러리를 사용하려는 사용자
- 미디어 데이터셋을 정리하거나 검수하는 데이터 분석가 및 연구 사용자
- 자동 태깅, 유사도 탐색, 장면 분석 등 선택적 AI 기능이 필요한 사용자

미래 확장 사용자는 현재 핵심 경험을 복잡하게 만들지 않는 범위에서 고려한다.

## 4. 핵심 제품 원칙

### 4.1 Local-first

**확정**

- 원본 미디어와 라이브러리 메타데이터는 기본적으로 사용자 장치에서 처리한다.
- 인터넷 연결 없이도 핵심 라이브러리 기능을 사용할 수 있어야 한다.
- 서버 장애나 사업 중단이 사용자의 로컬 데이터 접근을 막아서는 안 된다.
- 클라우드 기능은 로컬 제품을 대체하는 필수 계층이 아니라 선택적 확장 계층이다.

### 4.2 사용자 데이터 통제

**확정**

- 원본 파일의 위치와 보관 방식은 사용자가 결정한다.
- ClipPro는 사용자가 명시적으로 선택하지 않은 원본 미디어를 서버로 전송하지 않는다.
- 구독 해지나 라이선스 상태 변경으로 기존 로컬 데이터의 열람을 차단하지 않는다.
- 사용자는 자신의 라이브러리 메타데이터를 내보내거나 백업할 수 있어야 한다.

### 4.3 자연스러운 업그레이드

**확정**

- 유료 전환을 유도하기 위해 핵심 파일 접근이나 기본 탐색 경험을 의도적으로 훼손하지 않는다.
- 유료 기능은 규모, 자동화, 생산성 또는 지속적인 외부 비용에서 명확한 추가 가치를 제공해야 한다.
- 사용자가 결제하지 않더라도 이미 생성한 데이터가 손상되거나 사라지지 않는다.

### 4.4 미디어 중심의 단순성

**방향**

- 제품의 중심은 파일 관리 자체가 아니라 미디어를 의미 있는 단위로 정리하고 탐색하는 경험이다.
- 전문 기능을 추가하더라도 기본 사용자에게 불필요한 복잡도를 노출하지 않는다.
- 데이터셋 라벨링이나 AI 분석은 향후 별도 모듈 또는 작업공간으로 분리할 수 있다.

## 5. 현재 제품 범위

### 확정

초기 제품은 다음 기능을 중심으로 한다.

- 로컬 및 외장 저장소의 미디어 등록
- 미디어, 클립, 인물 및 컬렉션 관리
- 계층형 태그
- 사용자 정의 컬렉션
- 태그 규칙 기반 Smart Collection
- 이미지 및 영상 뷰어
- 클립 병합과 분리
- 워크스페이스 단위 데이터 구분
- 로컬 SQLite 기반 라이브러리
- 로컬 썸네일 및 분석 캐시

### 현재 제외 범위

- ClipPro 운영 서버에 원본 미디어 저장
- 다중 사용자 협업
- 웹 기반 전체 라이브러리 편집
- 필수 계정 로그인
- 필수 온라인 라이선스 검증
- 서버 기반 AI 처리
- 전문 데이터셋 라벨링

제외 범위는 영구적인 금지가 아니라 현재 제품 정체성과 출시 범위를 보호하기 위한 우선순위다.

## 6. Free / Pro 모델

### 방향

ClipPro는 초기에는 Free와 일회성 구매 방식의 Pro를 제공한다.

#### Free

- 핵심 미디어 관리 기능
- 로컬 라이브러리
- 태그 정의 수 제한
- Smart Collection 미지원

현재 내부 기준은 태그 정의 최대 50개다. 이 수치는 사용자 테스트와 실제 태그 사용량을 바탕으로 출시 전에 변경할 수 있다.

#### Pro

- 태그 정의 수 제한 없음
- Smart Collection
- 향후 추가되는 고급 생산성 기능

### 제품 원칙

- Free 제한은 데이터 손실이나 원본 접근 제한으로 연결하지 않는다.
- Pro 구매 이후 핵심 기능을 유지하기 위한 반복 결제를 요구하지 않는다.
- 무료 사용자가 제한에 도달하더라도 기존 태그와 데이터는 유지하고 열람할 수 있어야 한다.

## 7. 라이선스 및 업데이트 정책

### 방향

- Pro는 사용자 계정 또는 라이선스에 귀속되는 영구 사용권으로 제공한다.
- 초기 권장 활성화 수는 사용자당 3개 장치다.
- 사용자는 장치를 직접 비활성화하고 새로운 장치로 이전할 수 있어야 한다.
- 앱은 오프라인 상태에서도 장기간 정상 동작해야 한다.
- 온라인 검증은 매 실행 시 요구하지 않는다.

### 권장 라이선스 구조

라이선스는 UI의 단순한 `isPro` 플래그가 아니라 기능 권한 집합으로 다룬다.

예시:

```json
{
  "plan": "pro",
  "features": {
    "max_tags": null,
    "smart_collections": true,
    "cloud_sync": false,
    "ai_analysis": false,
    "dataset_labeling": false
  }
}
```

이 구조는 현재 Free/Pro만 제공하더라도 미래 기능을 기존 라이선스 모델을 깨지 않고 추가할 수 있게 한다.

### 미정

- 모든 메이저 버전의 평생 업데이트를 포함할지 여부
- 큰 제품 세대 변경 시 유료 업그레이드를 제공할지 여부
- 최종 가격 및 국가별 가격 정책
- 가족 또는 가구 단위 라이선스 제공 여부

제품 초기에는 단순성을 위해 평생 업데이트를 우선 고려하되, 장기 유지비와 제품 성숙도를 확인한 뒤 정책을 확정한다.

## 8. 인프라 방향

### 8.1 현재 단계

**확정**

현재 서버는 제품 데이터 저장소가 아니라 다음 기능만 담당한다.

- 결제 결과 처리
- 라이선스 발급과 복구
- 장치 활성화 및 비활성화
- entitlement 갱신
- 업데이트 메타데이터 제공

원본 미디어, 태그, 컬렉션, 인물 정보 및 사용자 메모는 기본적으로 서버로 전송하지 않는다.

권장 구조:

```text
ClipPro Desktop
├─ Local / External Media
├─ SQLite
├─ Thumbnail Cache
├─ Local License Cache
└─ Optional Network Client
          │
          ▼
License API
├─ Authentication
├─ License
├─ Device Activation
└─ Payment Webhook
          │
          ▼
License Database
```

### 8.2 데이터 소스 추상화

**방향**

미디어의 정체성을 운영체제 절대경로와 동일시하지 않는다.

```text
Media Source
├─ Local Folder
├─ Removable Drive
├─ OS-mounted NAS / SMB
├─ WebDAV
└─ ClipPro Cloud
```

DB에서는 다음과 같이 소스와 상대경로를 분리한다.

```text
source
- id
- source_type
- display_name
- root_locator
- volume_identity

media
- source_id
- relative_path
- file_identity
- content_hash
```

초기에는 로컬 폴더와 외장 드라이브만 구현하더라도, 도메인 계층이 특정 절대경로 형식에 직접 종속되지 않게 한다.

### 8.3 NAS 및 네트워크 드라이브

**방향**

NAS 지원의 첫 단계는 ClipPro가 SMB 프로토콜을 직접 구현하는 것이 아니라 운영체제에 마운트된 경로를 라이브러리 소스로 등록하는 방식으로 한다.

고려할 문제:

- 연결 끊김과 재연결
- 느린 메타데이터 조회와 썸네일 생성
- 드라이브 문자 또는 마운트 경로 변경
- NAS 절전 후 지연
- 운영체제별 파일 감시 차이
- 파일 잠금과 동시 수정

네트워크 드라이브의 원본은 원격에 두되, 썸네일과 탐색 메타데이터는 로컬에 캐시한다.

## 9. 클라우드 서비스 전략

### 방향

구독제는 ClipPro 애플리케이션 사용권이 아니라 지속적으로 서버 비용이 발생하는 선택적 클라우드 서비스에 적용한다.

```text
ClipPro Pro
- 일회성 구매
- 로컬 라이브러리 영구 사용

ClipPro Cloud
- 선택적 구독
- 백업 및 동기화
- 다중 장치
- 원격 접근
- 지속적인 저장 및 전송 비용
```

### 구독 해지 원칙

**확정 원칙**

- 구독 해지 후에도 로컬 라이브러리는 계속 사용할 수 있다.
- 클라우드 전용 데이터는 일정 기간 내보내기 기회를 제공한다.
- 삭제 일정과 백업본 제거 일정을 명확히 안내한다.
- 결제 실패를 이유로 사용자 원본 데이터에 즉시 접근 불가능한 상태를 만들지 않는다.

### 클라우드 구조 방향

```text
Desktop Sync Engine
├─ Local Database
├─ Change Journal
├─ Upload Queue
├─ Download Cache
└─ Conflict Resolver
          │
          ▼
Cloud API
├─ Account
├─ Subscription
├─ Device
├─ Sync Metadata
└─ Signed Upload / Download Authorization
          │
          ├─ PostgreSQL: 메타데이터
          └─ Object Storage: 미디어 객체
```

대용량 파일은 애플리케이션 서버를 경유하지 않고, 권한 검증 후 객체 스토리지에 직접 업로드하거나 다운로드하는 구조를 지향한다.

### 동기화 원칙

- SQLite 파일 전체를 여러 장치가 공유하거나 덮어쓰는 방식은 사용하지 않는다.
- 레코드 또는 변경 이벤트 단위로 동기화한다.
- 파일과 라이브러리 메타데이터의 동기화를 분리한다.
- 삭제는 즉시 물리 삭제하지 않고 일정 기간 tombstone으로 유지한다.
- 충돌 시 원본 보존을 우선하고 사용자가 복구할 수 있게 한다.

초기 클라우드 버전은 복잡한 범용 협업보다 1인 다중 장치 시나리오에 집중한다.

## 10. 데스크톱 보안 원칙

### 확정

ClipPro는 개인 파일과 민감할 수 있는 메타데이터를 다루므로, 데스크톱 애플리케이션 내부에서도 UI와 시스템 권한의 경계를 분명히 한다.

### WebView와 Rust Core

```text
React WebView
- 화면 렌더링
- 사용자 입력
- 최소 권한
- 파일시스템 및 비밀정보 직접 접근 금지

Rust Core
- 파일 접근
- 경로 검증
- SQLite 접근
- 라이선스 검증
- 인증 토큰 처리
- 네트워크 요청
```

### 권한 원칙

- Tauri capability는 기능별 최소 권한만 허용한다.
- 프론트엔드에 범용 파일시스템 또는 셸 권한을 부여하지 않는다.
- 사용자가 명시적으로 선택한 라이브러리 루트만 접근한다.
- 경로 정규화, 상위 경로 탈출 및 심볼릭 링크 우회를 검증한다.
- 외부 URL은 앱 WebView 안에서 임의 실행하지 않고 시스템 브라우저로 연다.
- 원격 JavaScript 및 불필요한 CDN 의존성을 사용하지 않는다.

### 업데이트 및 배포

- 업데이트 패키지는 서명하고 클라이언트에서 검증한다.
- Windows 설치 파일과 실행 파일은 코드 서명을 적용한다.
- macOS 배포 시 Developer ID 서명과 notarization을 적용한다.
- 업데이트 서명 키와 운영 배포 자격 증명은 분리하여 보관한다.

### 비밀정보 저장

다음 값은 SQLite나 일반 설정 파일에 평문으로 저장하지 않는다.

- refresh token
- 클라우드 접근 토큰
- 외부 AI API key
- 데이터베이스 암호화 키
- 복구용 비밀값

운영체제의 보안 저장소를 사용한다.

- Windows Credential Manager
- macOS Keychain
- Linux Secret Service

## 11. 개인정보 처리 원칙

### 11.1 로컬 처리

**확정**

기본 로컬 라이브러리에서 다음 데이터는 사용자 장치 안에서만 처리한다.

- 원본 사진과 영상
- 파일명과 경로
- 태그와 컬렉션
- 인물 이름 및 연결 관계
- 사용자 메모
- 썸네일과 분석 캐시
- 검색어와 탐색 기록

회사는 사용자가 클라우드 또는 외부 서비스를 명시적으로 활성화하지 않는 한 이 데이터에 접근하거나 수집하지 않는다.

### 11.2 서버가 처리할 수 있는 최소 데이터

라이선스와 결제를 위해 다음 정보는 서버에서 처리할 수 있다.

- 이메일 또는 계정 식별자
- 주문 및 결제 상태
- 라이선스 ID
- 활성화 장치 정보
- 앱 버전
- 보안 및 오류 대응을 위한 최소 기술정보

수집 목적, 보유 기간 및 삭제 절차를 개인정보 처리방침에 공개한다.

### 11.3 텔레메트리

**방향**

사용 분석과 자동 오류 보고는 기본 비활성화를 우선한다.

사용자가 선택적으로 동의하더라도 다음 정보는 수집하지 않는다.

- 파일명과 전체 경로
- 태그 및 컬렉션 이름
- 인물 이름
- 썸네일 또는 원본 미디어
- 검색어
- 사용자 메모
- 원본을 재식별할 수 있는 미디어 해시

오류 보고서는 전송 전에 로컬에서 경로와 사용자 콘텐츠를 제거한다.

### 11.4 클라우드 활성화

사용자가 ClipPro Cloud를 활성화하면 업로드되는 데이터와 목적을 기능 시작 전에 명확히 안내한다.

안내 항목:

- 업로드되는 데이터 종류
- 저장 위치와 국외 이전 여부
- 이용 목적
- 보유 기간
- 구독 해지 후 삭제 일정
- 처리위탁 사업자
- 암호화와 접근 통제 방식
- 데이터 내보내기 방법

### 11.5 AI 분석

외부 AI API를 사용하는 기능은 다음을 명시한다.

- 로컬 모델인지 외부 서비스인지
- 어떤 데이터가 어떤 제공자에게 전송되는지
- 제공자가 데이터를 보관하거나 학습에 사용하는지
- 사용자 API key를 사용하는지 ClipPro가 제공하는 크레딧을 사용하는지

외부 전송이 없는 로컬 분석과 외부 API 분석을 UI에서 구분한다.

## 12. 클라우드 보안 방향

### 최소 기준

- 전송 구간 TLS
- 비공개 객체 스토리지
- 저장 데이터 및 백업 암호화
- 사용자 및 워크스페이스별 접근권한 검증
- 최소 권한 IAM
- 짧은 유효기간의 업로드·다운로드 권한
- 관리자 MFA
- 운영 및 스테이징 환경 분리
- Secret Manager 사용
- 관리자 접근 감사 기록
- 탈퇴 및 삭제 작업 자동화
- 백업과 복구 절차 정기 검증

### 관리자 접근

**확정 원칙**

- 운영자 도구에서 고객 원본 미디어를 기본적으로 조회할 수 없게 한다.
- 고객 지원을 위한 데이터 접근이 필요하다면 사용자 동의, 접근 사유, 만료시간 및 감사 기록을 요구한다.
- 기술적으로 접근 가능한 것과 정책상 접근하지 않는 것을 구분하고, 가능한 경우 기술적으로 접근 자체를 제한한다.

### 클라이언트 측 암호화

**보류**

종단간 또는 클라이언트 측 암호화는 강한 개인정보 보호 기능이지만 다음 기능과 충돌한다.

- 웹 미리보기
- 서버 썸네일 생성
- 서버 AI 분석
- 계정 복구
- 공유
- 키 분실 복구

따라서 초기 클라우드 버전에서는 서버 측 암호화와 강한 접근 통제를 우선하며, 향후 선택적 Private Vault로 검토한다.

## 13. 미래 확장 모듈

### 13.1 AI Analysis

**보류**

가능한 기능:

- 이미지 및 영상 자동 태깅
- 장면 분류
- 유사 이미지 탐색
- 중복 및 근접 중복 탐지
- 품질 평가
- 얼굴 클러스터링
- 자연어 기반 라이브러리 검색

가능한 실행 방식:

- 로컬 모델
- 사용자 제공 API key
- ClipPro 제공 AI 크레딧

AI 기능은 처리 위치와 데이터 전송 여부를 명확히 표시해야 한다.

### 13.2 Dataset Labeling

**보류**

데이터 분석가와 연구 사용자를 위한 별도 작업공간 또는 모듈로 검토한다.

가능한 기능:

- Classification
- Bounding Box
- Polygon
- Segmentation
- Keypoint
- Label Review
- COCO, YOLO 등 내보내기

이 기능은 일반 개인 라이브러리 경험과 사용자 목적이 다르므로 기본 UI에 혼합하지 않고 명시적인 모듈 경계를 둔다.

### 13.3 모듈형 entitlement

미래 모듈을 고려해 라이선스 내부 구조는 기능 단위 entitlement를 지원한다. 다만 실제 판매 화면과 가격 정책은 제품이 해당 기능을 제공하기 전까지 노출하지 않는다.

## 14. 단계별 제품 진화

### Phase 1 — Local Personal Library

- 로컬 및 외장 드라이브
- SQLite 라이브러리
- 태그, 클립, 인물, 컬렉션
- Free / Pro 일회성 라이선스
- 서명된 업데이트
- 원본 미디어 서버 전송 없음

### Phase 2 — External Storage

- 운영체제에 마운트된 NAS 및 SMB
- 미디어 소스 추상화
- 연결 끊김과 재연결 처리
- 네트워크 원본에 대한 로컬 썸네일 캐시

### Phase 3 — Optional Cloud Subscription

- 계정
- 백업 및 동기화
- 다중 장치
- 객체 스토리지
- 변경 저널
- 충돌 복구
- 구독 해지 후 로컬 사용 유지

### Phase 4 — Optional Professional Modules

- AI Analysis
- Dataset Labeling
- 공유 및 협업 가능성
- 모바일 또는 웹 보조 클라이언트
- 선택적 Private Vault

각 Phase는 다음 단계의 구현을 전제로 하지 않는다. Phase 1은 독립적으로 완결된 제품이어야 한다.

## 15. 주요 비목표

ClipPro는 현재 다음 제품이 되는 것을 목표로 하지 않는다.

- 모든 파일 형식을 관리하는 범용 파일 탐색기
- 원본을 강제로 자체 저장소에 가져오는 클라우드 사진 서비스
- 여러 사용자가 동시에 편집하는 기업용 DAM
- 필수 구독형 SaaS
- 서버 연결이 없으면 사용할 수 없는 미디어 앱
- AI 생성 또는 분석이 중심인 서비스
- 전문 라벨링 도구를 기본 사용자 경험에 노출하는 복합 제품

비목표는 제품 집중도를 지키기 위한 기준이며, 사용자 검증 없이 기능 범위를 넓히는 것을 방지한다.

## 17. 의사결정 기준

새 기능 또는 비즈니스 모델을 검토할 때 다음 질문에 답한다.

1. 개인 데이터 관리 라이브러리라는 제품 정의를 강화하는가?
2. 사용자의 원본 데이터 통제권을 유지하는가?
3. 인터넷이나 회사 서버 없이도 핵심 기능이 유지되는가?
4. 일반 사용자에게 불필요한 복잡도를 추가하지 않는가?
5. 유료 제한이 실제 추가 가치 또는 지속 비용과 연결되는가?
6. 결제 상태 변화가 기존 데이터의 열람과 복구를 방해하지 않는가?
7. 어떤 데이터가 로컬을 떠나는지 사용자가 이해할 수 있는가?
8. 구현 편의가 장기 제품 원칙을 훼손하고 있지 않은가?

이 질문에 명확히 답하기 어렵다면 해당 기능은 제품 방향 또는 아키텍처 문서에서 먼저 검토한다.
